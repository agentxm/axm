# Architecture guides

Focused procedures for organizing an architecture docs corpus, creating one
concept governed by the Software architecture docs application profile, or
expressing and reviewing cross-cutting architecture claims. Choose the exact
task you need; use the foundations and root explainers for conceptual
understanding and the application profile for normative metadata and placement
rules.

## Corpus organization

- [Organizing an architecture docs corpus](organizing-an-architecture-docs-corpus.md) - How to grow a concise, navigable architecture docs corpus while giving every admitted concept a stable named identity from its first appearance.

## Demand and value

- [Documenting offerings](documenting-offerings.md) - How to create one Offering concept that defines a coherent value boundary without turning it into a product, capability, or software hierarchy.
- [Documenting audiences](documenting-audiences.md) - How to create one Audience concept for a durable, evidence-supported group without publishing private people, accounts, or research personas.
- [Documenting needs](documenting-needs.md) - How to create one Need concept that preserves a solution-independent problem, constraint, opportunity, or desired outcome.
- [Documenting Jobs to Be Done](documenting-jobs-to-be-done.md) - How to create one Job to Be Done concept grounded in evidence about progress sought in particular circumstances.
- [Documenting value propositions](documenting-value-propositions.md) - How to create one Value Proposition concept that scopes an evidence-bearing promise to an offering and audience.

## Abilities, behavior, and interaction

- [Documenting use cases](documenting-use-cases.md) - How to create one architecture Use Case with a subject, contextual actors, goal scope, main success scenario, material extensions, cross-view links, and precise evidence kept elsewhere.
- [Documenting capabilities](documenting-capabilities.md) - How to create one Capability concept with a declared bearer, level, outcome-oriented ability, and useful boundary.
- [Documenting features](documenting-features.md) - How to create one optional Feature concept whose recognizable behavior has durable identity beyond one use case, surface, implementation, or delivery item.
- [Documenting surfaces](documenting-surfaces.md) - How to create one Surface concept that defines an actor-facing encounter point independently of its structural realization.

## Product quality

- [Documenting product quality requirements](documenting-product-quality-requirements.md) - How to create one named, architecture-significant Product Quality Requirement with an ISO/IEC 25010 classification, explicit target and conditions, architectural consequences, and an authoritative assessment route.

## Responsibilities and invariants

- [Reviewing responsibilities with scenarios](reviewing-responsibilities-with-scenarios.md) - How to exercise representative use-case scenarios against architectural elements to find misaligned responsibilities, change spread, coupling, authority violations, and misplaced data variation.
- [Expressing invariants](expressing-invariants.md) - How to distinguish an invariant from neighboring requirements, state its scope and observation boundary precisely, and connect it to preservation obligations and evidence.

## Domain architecture

- [Documenting subdomains](documenting-subdomains.md) - How to create one Subdomain concept with a problem-space responsibility and justified core, supporting, or generic classification.
- [Documenting bounded contexts](documenting-bounded-contexts.md) - How to create one Bounded Context concept that declares a coherent model, language, authority, and boundary.
- [Documenting context maps](documenting-context-maps.md) - How to create one Context Map concept that makes directional inter-context relationships and their consequences explicit.

## C4 structure and views

- [Documenting C4 software systems](documenting-c4-software-systems.md) - How to create one C4 Software System concept with a clear value, responsibility, boundary, and interaction context.
- [Documenting C4 containers](documenting-c4-containers.md) - How to create one C4 Container concept for an application or data store inside a declared software system.
- [Documenting C4 components](documenting-c4-components.md) - How to create one C4 Component concept with a cohesive responsibility, defined interface, and exactly one owning container.
- [Documenting C4 views](documenting-c4-views.md) - How to create one selected C4 View that answers a primary question using consistent canonical elements and relationships.
