# Plan

Use only after deliberate `$plan` selection. Natural-language similarity or a
Ready Design does not activate this stage.

Read through active AXM scope; in this workspace read:

1. `knowledge/gen-stack/src/processes/running-change-realization-stages.md`;
2. `knowledge/gen-stack/src/processes/deciding-and-realizing-software-changes.md`;
3. `knowledge/gen-stack/src/implementation/planning-change-implementation.md`.

## Predecessor

Verify the exact Specification is persisted `Accepted`, the exact Design is
persisted `Ready`, both have no Open items, their bindings reconcile, and
authoritative readback is current. Persist Design `Ready → Accepted` in place
before planning. Stop on any Draft, stale, conflicting, open, or unverified
input.

## Boundary

Plan owns one evidence-guided implementation course: affected units,
dependencies, increments, required Protocol feedback, proportional focused
review checkpoints, exit evidence, rollout, recovery, risks, return conditions,
state, and Open items.

It does not rewrite desired meaning or Design, create external implementation
records, assign, estimate, prioritize, implement, review, or release. Derived
host-native task projection is outside both Plan and Sync Change.

## Work

1. Bind exact artifact and current Implementation revisions, authorities,
   canonical target, and host revision.
2. Inspect realized units, interfaces, dependencies, state, evaluation
   machinery, operations, and repository instructions.
3. Map Requirements, Architecture, and every required Protocol to realization
   and evidence paths.
4. Sequence architecture-bearing prerequisites before dependent behavior unless
   a named compatibility, migration, safety, or atomicity constraint requires
   interleaving.
5. Put required Protocol feedback at its earliest credible point, with
   re-execution triggers, Result control, and final exact-revision evidence.
6. Define independently implementable, reviewable, reversible, and verifiable
   increments.
7. Disposition Architecture, Requirements, Evaluations, and Implementation
   review. Create a focused checkpoint only for a materially affected focus;
   combine focuses that share one stable subject and control condition.
8. Require fresh integrated final review separately from Protocol execution and
   checkpoint feedback.
9. Plan rollout, observation, rollback or forward recovery, and irreversible
   points proportionately.
10. Put unresolved upstream decisions in Open items and return them to their
    owners.

## Stage completion

Apply the shared lifecycle, persistence, presentation, and invalidation
contract. A plan is Ready only when the Guide's complete conditions, exact
current bindings, verified canonical revision, and `- None.` under Open items
all hold. `$implement` accepts that exact revision.

Ready plan acceptance does not grant repository mutation authority.

## Output

Use the exact portable first-screen order and vertical work, Evaluation, and
review cards in `Planning change implementation`. Preserve performed versus
planned evidence and do not invent owners, estimates, priorities, dates, or
external records.

Recommend `$implement` only when Ready; otherwise name the smallest upstream
return. Do not activate it.
