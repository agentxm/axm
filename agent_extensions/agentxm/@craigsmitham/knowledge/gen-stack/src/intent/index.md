# Intent

Intent captures human-oriented direction about desired outcomes and why they
matter. These concepts describe value, actors, goals, problem-space context,
and strategic orientation that may source canonical Requirements but do not
themselves own binding obligations.

## Value and demand

- [Offerings and value](offerings-and-value.md) - How offerings connect audiences, needs, jobs to be done, and value propositions to goal-oriented behavior and architecture without forcing them into one product hierarchy.
- [Jobs to Be Done](jobs-to-be-done.md) - How Jobs to Be Done explains demand as progress sought in particular circumstances, and how jobs relate to needs, offerings, use cases, capabilities, domain meaning, and software structure.
- [Documenting offerings](documenting-offerings.md) - Use when a coherent value boundary needs identity distinct from product, Capability, or software hierarchies; create one Offering concept.
- [Documenting audiences](documenting-audiences.md) - Use when a durable, evidence-supported group affected by or receiving value from an Offering needs explicit identity; create one Audience concept without publishing private people, accounts, or research personas.
- [Documenting needs](documenting-needs.md) - Use when evidence reveals a solution-independent problem, constraint, opportunity, or desired outcome worth preserving; create one Need concept.
- [Documenting Jobs to Be Done](documenting-jobs-to-be-done.md) - Use when evidence shows progress sought in particular circumstances and that progress needs solution-independent identity; create one Job to Be Done concept.
- [Documenting value propositions](documenting-value-propositions.md) - Use when an evidence-bearing promise must be scoped to one Offering and Audience; create one Value Proposition concept.

## Goals and problem space

- [Goal-oriented behavior and use cases](goal-oriented-behavior.md) - How use cases connect actor goals and subject behavior to capabilities, interaction surfaces, domain authority, software responsibilities, dynamic views, and executable evidence.
- [Documenting use cases](documenting-use-cases.md) - Use when actor-goal interactions need a scenario-centered behavioral view; create one Use Case with contextual actors, goal scope, success path, material extensions, cross-view links, and evidence kept elsewhere.
- [Documenting subdomains](documenting-subdomains.md) - Use when a problem-space responsibility needs explicit identity and a justified strategic classification; create one Subdomain concept as core, supporting, or generic.
