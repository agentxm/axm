# Software structure

Explanation and authoring guidance for C4 Software Systems, Containers,
Components, and selected structural views.

- [C4 model](c4-model.md) - How the C4 model uses hierarchical abstractions and selected diagrams to communicate software structure at different levels of detail, and where it needs complementary architecture views.
- [Developing C4 structure](developing-c4-structure.md) - Use when greenfield design or brownfield runtime evidence suggests missing, underdeveloped, misplaced, or disputed software boundaries and responsibilities; develop candidate C4 elements and views without mirroring the implementation inventory.
- [Documenting C4 software systems](documenting-c4-software-systems.md) - Use when an accepted software-system boundary and value need canonical C4 representation; record one Software System concept with clear responsibility and interaction context.
- [Documenting C4 containers](documenting-c4-containers.md) - Use when an accepted application or data-store boundary inside a declared Software System needs canonical identity; record one C4 Container with its responsibility and technology boundary.
- [Documenting C4 components](documenting-c4-components.md) - Use when an accepted cohesive responsibility inside one C4 Container needs canonical identity; record one Component with a defined interface and exactly one owning Container.
- [Documenting C4 views](documenting-c4-views.md) - Use when accepted C4 elements need a selected perspective for one architectural question; record one View using consistent canonical elements and relationships.
