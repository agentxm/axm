# Agent surface research refresh, 2026-11-10

Point-in-time primary-source research for capability-catalog maintainers. This
is evidence for proposed catalog maintenance, not a compatibility certification
or a replacement for the TypeScript catalog. Source baseline:
`f8dd4c981`. No vendor runtime, installation, publication, or authentication
flow was exercised. “Documented” below means vendor documentation was read.

The sample covers the requested major product families and several established
extension hosts. It is purposeful coverage, not a market-share ranking or a
census of every catalog target. Pricing and model-quality rankings are outside
this refresh. Read the [maintenance contract](README.md) before promoting any
finding into executable catalog data.

## Product names and execution boundaries

### Claude and Claude Code

Anthropic announced the merger of Cowork and chat into **Claude** on September
16, 2026. Its current help page describes a unified conversation that can answer
questions or deliver research, reports, spreadsheets, and presentations. Team
and Enterprise availability depends on the unified-experience setting. This is
not evidence that every legacy Cowork interface has disappeared from every
account. [Announcement](https://claude.com/resources/articles/cowork-is-now-claude),
[current availability](https://support.claude.com/en/articles/16761823-claude-cowork-and-chat-are-one-claude).

Claude Code remains a distinct integration contract. Its plugins bundle skills,
agents, hooks, MCP servers, and other components and can be loaded from a local
folder or marketplace. Shared branding does not establish identical execution
semantics in hosted Claude. [Claude Code plugins](https://code.claude.com/docs/en/plugins).

Catalog action: review `cowork.ts` and `claude-ai.ts` together. Their separate
product labels and unconditional chat-versus-Cowork restrictions no longer
adequately explain the unified experience. Preserve target IDs until the
successor contract and rollout conditions are resolved. In particular, do not
infer that plugin hooks or subagents now run in every conversation merely from
the brand merger. Review each capability against its current reference.

### ChatGPT Work and Codex

The official name is **ChatGPT Work**. It completes multistep tasks using files,
plugins, and approved tools, and supports recurring work. Local execution and
cloud-coordinated work with connected-computer access have different availability
and execution constraints. OpenAI describes Work and Codex as sharing core
capabilities, with Work oriented toward everyday work.
[Work overview](https://learn.chatgpt.com/docs/get-started-with-work).

ChatGPT and Codex share a plugin directory. Plugins can contain skills, MCP
servers, optional UI, and lifecycle hooks; scripts still need to exist in the
execution environment. Directory installation alone does not deploy scripts.
[Plugin architecture](https://developers.openai.com/plugins/concepts/plugins).
Standalone skills are documented for desktop, Codex CLI, and IDE; plugin skills
also reach Chat and Work on web and mobile.
[Skill delivery](https://developers.openai.com/codex/skills).

Catalog action: expand `chatgpt.ts`'s product/surface explanation to name Work and
its local/cloud distinction. Review `codex.ts` alongside it, but do not duplicate
filesystem ownership or assume that a desktop skill path provisions a hosted
account. Current catalog delivery remains authoritative until those changes are
implemented and verified.

### Cursor, Grok Build, Grok Bot, and Grok

Cursor's August 14 announcement confirms its acquisition by SpaceX. The catalog
already records that parent relationship. Ownership does not merge integration
targets. [Cursor announcement](https://cursor.com/blog/joining-spacex).

Cursor documents both portable Agent Plugins (skills and MCP) and its richer
Cursor Plugins format (also rules, agents, commands, hooks, and variables).
The documentation explicitly distinguishes variable expansion: portable
`${PLUGIN_ROOT}` and `${PLUGIN_DATA}` are not expanded in `mcp.json`; Cursor's
root variable is `${CURSOR_PLUGIN_ROOT}`. Team skill publishing and marketplace
installation are separate actions.
[Cursor plugins](https://cursor.com/docs/plugins).

Grok Build is the coding CLI. It documents skills, plugins, hooks, MCP, LSP,
and child sessions. It reads `.grok` content and documents compatibility readers
for Claude content and user `.agents` skills. Treat broad vendor compatibility
language as a claim requiring grammar and runtime checks, especially for tool
permissions and hook behavior.
[Grok Build extensions](https://docs.x.ai/build/features/skills-plugins-marketplaces).

Grok Bot is a separate hosted work product: bots use persistent cloud computers,
plugins, custom MCP servers, and can delegate coding to Cursor Cloud Agents.
Its documented skills and routines support reusable and scheduled work. Grok's
chat app is a different product; Grok Bot's FAQ identifies Cursor sign-in.
[Bot execution](https://docs.x.ai/grok-bot/how-grok-bot-works),
[Bot overview](https://docs.x.ai/grok-bot/overview),
[identity and access](https://docs.x.ai/grok-bot/faq).
Grok's web/mobile skill offering also includes document, spreadsheet, and deck
workflows. [Grok skills](https://x.ai/news/grok-skills).

Catalog action: retain `cursor` and `grok-cli` as distinct IDs. No `grok-bot`
record exists at the inspected baseline. Investigate a separate hosted target,
including artifact import/export, authentication, and install ownership; a
persistent cloud filesystem does not by itself make AXM local projection valid.
Do not describe all Grok capabilities through the Build record.

## What this evidence changes

1. Prioritize identity and surface corrections for unified Claude, ChatGPT Work,
   and Grok Bot before expanding broad “supported agent” marketing claims.
2. Treat skills as a useful portable baseline and plugin manifests as separate
   packaging contracts. Shared SKILL.md syntax does not standardize permissions,
   tool names, hook events, dependencies, credentials, or hosted delivery.
3. Promote only reviewed claims into `profile.review` or `native.review`.
   Preserve the existing `axm.verification` dates: this was documentation review.
4. For each proposed adapter change, establish project/user/hosted scope,
   precedence, ownership, installation, update, removal, and unavailable-account
   behavior before changing executable support. Native support and AXM delivery
   remain separate decisions.

The research is complete for this stated source sample. Catalog remediation,
vendor execution, plugin-format conformance, and release adoption remain
separate work. Recheck this snapshot by 2026-12-10 or sooner on a vendor rename,
contract change, or rollout update.
