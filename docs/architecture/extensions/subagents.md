# Subagents

A Subagent is a reusable delegated-agent profile that AXM adapts to the native
subagent surface of each configured agent.

## Responsibilities

AXM preserves one package identity with an optional portable instruction core
and explicit runtime implementations. Selection is deterministic: a declared
customized or native implementation takes precedence for its runtime; otherwise
a compatible adapter can render the core. Unsupported targets are reported
explicitly and never projected as Skills.

## Non-responsibilities

AXM does not schedule delegation, choose when a parent agent delegates, define
an industry subagent standard, or promise equivalent model, tool, permission,
or security behavior across runtimes. Native configuration keeps its host's
semantics. AXM does not relocate supporting native resource trees.

## State and realization

The package manifest owns package identity and explicit implementation
selection. A core owns shared instructions and may declare a distinct native
role name. A customized implementation applies only its declared native
configuration and instruction change. A complete native implementation owns its
native identity, configuration, and instructions; it does not inherit the core.

Canonical acquisition preserves the package tree. Every declared source
reference must remain contained and present, including after publication
filtering. Acquisition, activation, and projection remain distinct: a disabled
package can be retained without a compatible target, while enabling a package
with configured targets requires at least one compatible implementation.
Mixed support realizes compatible targets and reports the others. Sync may
retire old owned output when accepted state no longer supports any target.

Preview, apply, lint, render inspection, and currency use the same selection and
compiler. Read-only render inspection can select a catalog runtime independently
of workspace membership. Generation depends on the selected implementation;
an unused variant does not invalidate another runtime's output.

## Ownership and coexistence

The native ownership unit is one profile file or one named entry supported by
the adapter. Profiles with distinct native identities can coexist. A supported
syntax alone does not establish a supported writer: placement, ownership proof,
and safe withdrawal must all be available.

AXM may rewrite or remove only profiles traceable to the accepted package.
Name or path alone is not ownership evidence. Changing a native identity retires
obsolete owned output without deleting unrelated native definitions or Skills.
Shared physical destinations require identical generated bytes for every
consumer; incompatible claims fail before mutation.

## Invariants

- An invalid explicit implementation fails validation rather than selecting the core.
- Native identity is independent of package identity.
- No universal native model, tool, permission, or security defaults are inferred.
- Import preserves native source bytes and fills only an empty authored runtime slot.
- Unowned native profiles are preserved; collisions block the affected mutation.
- Disabling removes owned projections while retaining desired and canonical state.

## Testing strategy

Executable specifications cover explicit selection, package containment and
filtered publication, native import and stale previews, read-only rendering,
mixed and zero support, ownership collisions, physical aliases, generation
currency, activation, safe removal, and acquisition across source families.
Native adapter cases establish supported behavior and explicit refusal without
claiming that AXM controls the host's runtime decisions.
