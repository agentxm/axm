# Requirements

Explanations, principles, and authoring guides for turning accepted Intent into
one canonical, subject-centered obligation and connecting that authority to
Architecture, Implementation, and Evaluations.

## Engineering and authority

- [Requirements engineering in software architecture](requirements-engineering.md) - How Intent, Architecture, and recognized sources co-develop into accepted subject-centered obligations, and how requirement quality, validation, verification, traceability, and evidence remain distinct.
- [Classifying requirements in software architecture](requirement-classification.md) - How to choose one primary profile requirement type from the obligation itself while using standards classifications as complementary lenses rather than competing authorities.
- [One authority, many witnesses](one-authority-many-witnesses.md) - Why an accepted Requirement has one normative authority while architecture, implementation, tests, evaluations, and telemetry may repeat its predicate for different purposes.
- [Reviewing a requirement set](reviewing-requirement-sets.md) - Use when a bounded Requirement set needs joint review before reliance; assess completeness, consistency, feasibility, comprehensibility, and coverage of source needs without treating an open-world corpus as a complete specification.

## Authoring workflow

- [Developing Requirements](developing-requirements.md) - Use when intent, a change, a defect, or implementation evidence suggests a missing, underdeveloped, misplaced, or disputed obligation; develop a candidate Requirement and subject without treating inference, derivation, or a test as acceptance.
- [Documenting requirements](documenting-requirements.md) - Use when an accepted obligation needs canonical subject-centered expression; transform it into a Requirement, review its engineering, preserve rationale and traceability, and connect it to architecture and evidence.
- [Specifying Requirement changes in software work items](/work-items/specifying-requirement-changes.md) - Use when Requirement-impact analysis identifies a candidate addition, revision, retirement, or replacement; specify the desired-state delta, identity and lineage, authority, blockers, and downstream consequences without making the work item normative.
- [Selecting a requirement specification method](selecting-a-requirement-specification-method.md) - Use when an accepted obligation needs a fitting expression or analysis approach; select any method by semantic fit, quality contribution, authority clarity, and proportionate lifecycle cost without treating documented methods as an allowlist.

## Specification methods

This portfolio is illustrative and open to any method that preserves authority
and helps the Requirement or set satisfy its quality criteria.

- [Easy Approach to Requirements Syntax (EARS)](easy-approach-to-requirements-syntax.md) - How EARS structures textual requirements through ordered optional-feature, state, trigger, subject, imperative, and response clauses.
- [Writing requirements with EARS](writing-requirements-with-ears.md) - Use when an accepted subject-centered obligation needs an EARS statement; select, order, compose, and review its clauses without changing the obligation's authority.
- [Specifying external-conformance requirements](specifying-external-conformance-requirements.md) - Use when an accepted obligation requires a subject or artifact to conform to an external standard, specification, schema, or profile; identify the exact normative target and preserve separate local acceptance, external meaning, and bounded evidence.
- [Expressing invariants](expressing-invariants.md) - Use when a condition must remain true across a declared observation boundary; classify the invariant, admit accepted preservation obligations as Requirements, and connect them to architecture, enforcement, and evidence.

## Requirement types

- [Documenting functional requirements](documenting-functional-requirements.md) - Use when an accepted obligation specifies behavior, response, transformation, state transition, or preservation; document one functional Requirement without confusing it with quality, constraints, or implementation.
- [Quality requirements in software architecture](product-quality.md) - How accepted system, product, service, and data quality outcomes become assessable, subject-centered Requirements that applicable quality models classify without generating obligations or owning evidence.
- [Documenting quality requirements](documenting-product-quality-requirements.md) - Use when an accepted system, product, service, or data quality outcome must be assessable; engineer and document one quality Requirement using the unified model and applicable classification.
- [Documenting process requirements](documenting-process-requirements.md) - Use when system lifecycle, development, operation, or governance must satisfy a durable outcome; document one Process Requirement without turning plans, tasks, or corpus rules into system requirements.
- [Human-centred requirements in software architecture](human-centred-requirements.md) - How usability and human-factors requirements overlap while preserving different primary outcomes, contexts, evidence, and architecture consequences.
- [Documenting human-factors requirements](documenting-human-factors-requirements.md) - Use when an accepted obligation arises from human capabilities, limitations, workload, safety, health, cognition, or operating environment; document one human-factors Requirement.
- [Documenting usability requirements](documenting-usability-requirements.md) - Use when an accepted outcome of use must be stated for specified users, goals, tasks, resources, and context; document one usability Requirement without prescribing an evaluation method.
- [Documenting constraint requirements](documenting-architecture-constraints.md) - Use when an accepted architecture subject must be limited to a permitted design, implementation, technology, interface, legal, policy, platform, or operating space; document one binding constraint Requirement.
