# Design: resolve-plan interaction split (kernel-destined modules stop importing CLI modules)

Scope: `packages/extension-management/src/unstable/` in worktree `/home/exedev/Code/agentxm/wt/axm-pkg-arch`.
Goal for this stage: `plan/` (→ `@agentxm/workspace-operations`) and `workspace/` (→ `@agentxm/workspace-state`) — plus the other listed violators (`auth/`, `mcps/`, `packs/`, `publish/`) — stop importing `cli-renderer/`, `cli-flags/`, `cli-prompt/`, `cli-runtime/`, `cli/prompt/`. Interaction- and renderer-backed implementations move INTO the CLI-destined modules (`cli-runtime/`, `cli-renderer/`, `cli/prompt/`), which later move to the CLI package. This is a responsibility relocation, not a plan-engine redesign.

Out of scope (recorded, untouched): `app-error/` imports from kernel modules (the architecture doc also bans kernel `AppError`, but it is not in this stage's violation list and is pervasive); `workflows/` own use of `CliRenderer`/`PromptCancelled` (feature-destined, not kernel); `telemetry/` living in extension-management (CLI-destined per doc).

---

## Load-bearing findings from the code

1. **`cli-runtime/confirmation-recovery.ts` is not runtime code.** It is pure data (`ConfirmationRecovery`, `PlanExecution`, `ConfiguredAgentOperation`) plus pure string/`SuggestedAction` builders. It already imports `plan/plan.js` (`PlanPolicyId`). The kernel's `previewOrApplyPlan` takes `PlanExecution` as its input and builds resolutions from `confirmationRecoverySuggestions`/`namedPolicyRecoverySuggestions`. The type is part of the kernel API and must move to `plan/`.
2. **`ResolvePlanInteraction` is already the right seam** for the confirm step; its definition file just lives in `workspace/` and drags in `cli/prompt` (`requireInteractive`), `cli-runtime` (recovery suggestions), and `cli-prompt` (`PromptCancelled`). It needs relocation to `plan/`, widening (display + progress + availability), and its Live split out into `cli-runtime/`.
3. **`resolve-plan.ts` renderer usage is exactly four presentation moments**: (a) spinner around `augmentPlanWithReconciliation`; (b) `displayPlan` gated on `mode/verbosity/confirmable-risk`; (c) `renderer.step` inside `acquireTransition`'s `onWaiting`; (d) spinner around apply with a `subscribeToLifecycle` subscription mapping `UnitStarted`/`UnitResolved`/`PhaseStarted("restoration")` to spinner updates. All four fold into the widened interaction service.
4. **`PromptCancelled` never escapes `previewOrApplyPlan`** — it is caught and mapped to `confirmed = false` (declined). So the plan module can model cancellation as a _value_, not an error. `PromptCancelled` stays in `cli-prompt/` for CLI-side flows (`select-skills`, `command-actions`, workflows' own actions) and for the runtime envelope (exit 0 + "cancelled" result, `cli-runtime/runtime-envelope.ts:89,93,136,336`).
5. **`WorkspaceInitializationInteraction` methods DO leak `PromptCancelled` upward**: `bootstrapWorkspace` failures flow to the CLI envelope, which maps `PromptCancelled` → exit success/"cancelled". Replacing it needs a kernel-owned cancellation error that the envelope also recognizes.
6. **Auth's `DeviceLoginInteraction`/`AuthLoginInteraction` (browser/clipboard, spawner-backed) are already CLI-free** and can stay in `auth/`. They cannot absorb the renderer calls — that would drag `CliRenderer` into `auth/`. A new presenter seam is needed for rendering (spinners, instructions, URL/code presentation, machine-mode `renderer.result` emission).
7. **The machine-vs-human decision gates side effects in device login**: in machine mode (`renderer.result` returns true) the browser is NOT opened and the clipboard is NOT written. Any presenter design must preserve that ordering (emit-first, side-effects only on the human path).
8. **`isCI` is env detection, not a flag** (`envOption("CI")` from `utils/environment.js`); it belongs in `utils/environment.ts`. Consumers: `cli-flags/non-interactive.ts` (chain), `auth/credential-store.ts` (violation), `telemetry/client.ts` (CLI-destined, import just repoints).
9. **`isNonInteractiveOptional` in `mcps/operations/install.ts` is a fail-closed backstop** (missing required inputs + non-interactive → usage error). The operation args are built at 6 CLI sites; a plain boolean on the op args is the honest input.
10. **`setup.ts:764` forces non-interactive bootstrap by providing `nonInteractiveFlag` as `Option.some(true)`** — after parameterizing initialization on an options boolean, that provideService no longer reaches initialization and must become an explicit `nonInteractive: true` option (correctness point for slice 4).
11. Test defaults that matter: `TestFlagsLayer` defaults `nonInteractive` to `Option.some(true)`; `plan/resolve-plan.internal.test.ts` and `workspace/service.internal.test.ts` rely on that default. Replacement test seams should default to "confirmation unavailable"/explicit `nonInteractive: true` to minimize behavioral churn.

```ts
import * as Option from "effect/Option";
import * as ServiceMap from "effect/Context";
import * as Layer from "effect/Layer";
import type { AppError } from "../app-error/index.js";
import type { ConfirmationRecovery } from "./plan-execution.js";
import type { Plan } from "./plan.js";

/** Outcome of the apply confirmation. `cancelled` is the typed successor of a
 * caught PromptCancelled at the CLI implementation; the kernel treats it as
 * declined today but the distinction is preserved for resolutions. */
export type ApplyConfirmation = "approved" | "declined" | "cancelled";

export interface ResolvePlanInteractionService {
  /** Whether an interactive confirmation can be obtained (CLI Live: !isNonInteractiveOptional). */
  readonly isConfirmationAvailable: Effect.Effect<boolean>;
  readonly confirmApplyChanges: (
    recovery: ConfirmationRecovery,
  ) => Effect.Effect<ApplyConfirmation, AppError>;
  /** Present the immutable candidate. The implementation owns the
   * verbosity/quiet/mode gate and all wording. Kernel calls unconditionally. */
  readonly presentPlan: (
    plan: Plan<unknown, unknown>,
    options: { readonly mode: "preview" | "apply" },
  ) => Effect.Effect<void>;
  /** Progress envelope for lockfile reconciliation ("Resolving <name>"). */
  readonly withPlanningProgress: <A, E, R>(
    planName: string,
    run: () => Effect.Effect<A, E, R>,
  ) => Effect.Effect<A, E, R>;
  /** Progress envelope for apply. The implementation subscribes to the
   * operation lifecycle stream itself (plan/operation-events) and maps
   * UnitStarted/UnitResolved/PhaseStarted(restoration) to progress updates. */
  readonly withApplyProgress: <A, E, R>(
    planName: string,
    run: () => Effect.Effect<A, E, R>,
  ) => Effect.Effect<A, E, R>;
  /** Transition-lock contention notice (was renderer.step in onWaiting). */
  readonly noteTransitionWait: (
    holder: Option.Option<{ readonly command: string; readonly pid: number }>,
  ) => Effect.Effect<void>;
}

export class ResolvePlanInteraction extends ServiceMap.Service<
  ResolvePlanInteraction,
  ResolvePlanInteractionService
>()(
  "@agentxm/extension-management/unstable/plan/resolve-plan-interaction/ResolvePlanInteraction",
) {}
```
