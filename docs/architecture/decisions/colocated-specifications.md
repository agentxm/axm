# Colocated specifications

Supersedes the identity, project-ownership, result-adapter, and governance
sections of [Specification infrastructure decisions](specification-infrastructure.md).

## Decision

A specification is a `*.spec.ts` file that lives beside the source it
governs, inside the project that owns that source. The central
`specifications` project holds only the generated catalog, the local
product-goal registry, and the specifications not yet moved; it is not a
required home for any specification.

- **Identity is independent of path.** `requirement` is the stable
  identity, declared in metadata as two or more kebab segments joined by
  `/`. Existing identities, including `cli/...` prefixes, are preserved when a
  file moves. Exactly one canonical `*.spec.ts` per identity exists across all
  authored roots; a second file for the same identity fails discovery,
  hygiene, and the catalog. Moving a file preserves identity and history.
- **Discovery is per owner, inferred from the project graph.**
  `scripts/workspace-discovery.ts` reads the Nx project graph and its file
  map: a project exists because its `project.json` exists, and a file belongs
  to the nearest project root above it. A `*.spec.ts` is accepted only when
  its owner ships runtime code (`domain:*` or `role:application`), is an
  end-to-end project (`role:e2e`, boundary specifications beside their
  execution bindings), or is the retiring catalog project
  (`type:specification`); it must sit under the owner's source root or its
  `specifications/` directory. Nothing is a hand-maintained inventory of
  areas, packages, or directories. A Git ref is read the same way from
  `git ls-tree`, so both sides of a verdict resolve ownership identically
  across layouts.
- **Purpose is labelled per file at execution.** Every owner's test target
  runs specifications and ordinary tests together; the shared
  `vitest.purpose.setup.ts` labels each file `specification`, `e2e`, or
  `test` from its suffix, requires a valid exported `specification` for a
  `.spec.ts`, joins the metadata onto the native results, and records the
  purpose in the execution receipt. A `.spec.ts` receipt that did not run
  under specification labelling, or that is missing, stale, skipped, filtered,
  or partial, is never a pass.
- **The verdict digests three layers.** The contract digest covers metadata
  and bound evidence; the example digest covers ordered `describe`/`it`/
  `test` titles and `each` rows; the body digest covers the comment-free,
  whitespace-normalized AST. Per identity, in order: `added`, `removed`,
  `revised-contract`, `possibly-revised-rule` (examples changed; reviewed as a
  possible requirement change), `moved` (path changed, everything else
  equal), `revised-evidence` (body only; not reviewed for meaning by tooling),
  `implementation-impact`, unchanged. Only entries with no change kind count
  as unchanged.
- **Removals are explained or visibly unexplained.** An optional
  `specifications/disposition-ledger.json` (an array of
  `{ requirement, disposition, successor?, basis }` with dispositions
  `converted-to-test`, `engineering-policy`, `retired`, `superseded-by`)
  explains a removed identity; a successor's `supersedes` entry explains it
  implicitly; anything else renders as an unexplained removal, allowed but
  visible.
- **Governance follows the file pattern.** `.github/CODEOWNERS` routes
  `**/*.spec.ts` to maintainer review wherever the file lives, alongside the
  catalog directory. The catalog is generated by
  `axm:generate:specification-catalog` into `specifications/catalog.md`,
  organized by role, primary product goal, and review class, naming each
  specification's owner and linking its canonical file; generation never
  executes a specification.
- **Selection resolves to owners.** `pnpm test:spec` resolves identities,
  classes, or characteristics to owner projects and runs each owner's own
  `test` target with the project-relative files, so selection needs no
  central test project.

## Context

The central `specifications` project tied identity to path, ran every
specification through one harness, and grouped the catalog by directory. As
packages are classified by domain and role and the corpus moves beside its
owners, the verification tooling had to stop assuming one root, one project,
and one directory-derived identity, and it had to distinguish a move from a
removal plus an addition. The corpus itself moves separately; this decision
makes every piece of infrastructure work for a specification located in any
authored project first.

## Alternatives considered

- **Keep a central specification project and colocate only tests.**
  Rejected: the central project could not express which package a
  requirement governs, needed a harness that reached every package, and
  made every move an identity change.
- **Derive identity from the colocated path.** Rejected: paths change with
  package placement, and identity must survive that; a stable declared
  identity is what the verdict keys on.
- **A hand-maintained list of specification areas or owners.** Rejected:
  every scanner that enumerated directories silently skipped whatever it did
  not know about; the project graph already knows every project and file.
- **Treat any byte change as evidence maintenance.** Rejected: renaming or
  re-tabling decisive examples changes what a requirement is adjudicated by
  and must be reviewed; formatting must not.

## Consequences

- Every owner `vitest.config.ts` declares `makeTestReporting({ project })`
  and `setupFiles: [purposeSetupFile]`; a project with several test targets
  names each suite distinctly.
- A change to discovery, placement inference, purpose labelling, or
  reporting invalidates every cached test, typecheck, catalog, and hygiene
  target through `sharedGlobals`.
- Source hygiene enforces the discovery rules: a `.spec.ts` exports a valid
  `specification` with a unique identity, a `.test.ts` never does,
  `.e2e.test.ts` lives only in `role:e2e` projects, neither lives in
  `__generated__/`, and symbolic links may not hide them.
- The fast-suite budget sums specification file time across every owner's
  JUnit output; the 360-second budget from the superseded record carries
  forward, and raising it is a deliberate revision of this record.
- The shared contract package is a dependency of every project that owns a
  specification; the contract package itself must not depend on any project
  that owns specifications, or the build graph cycles.

## Reconsideration

Reconsider when a project needs to own specifications without shipping
runtime code or binding boundary executions, when title-level example capture
demonstrably misses meaningful example changes, or when the project graph
stops being the authority for project membership and file ownership.

Accepting authority: maintainer approval through the pull-request workflow.
Binding obligation: this record owns the verdict classification — added,
removed, revised, and possibly revised requirement contracts separated from
moved files, changed verification coverage, and changed implementation inputs,
each requirement keyed by its stable identity rather than its path.
`scripts/specification-verdict.test.ts` is its enforcement.
